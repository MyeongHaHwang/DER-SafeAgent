# Threat Model — DER-SecAgent

## Scope
**In scope:** cyber attacks against the DER cyber-physical control loop reachable
from the utility-side network or a compromised aggregator account, including
manipulated telemetry, forged commands, and replayed sessions over IEC 61850
(GOOSE/MMS) or DNP3.

**Out of scope:** physical tampering with hardware, GPS spoofing of grid timing
(separate threat program), pure ransomware impacting only IT systems, supply-chain
firmware compromise that subverts the DER firmware-attestation pipeline (treated
in a sibling work).

## Assets and surfaces
| Asset | Protocol surface | What an attacker controls if owned |
|---|---|---|
| Smart inverter (PV) | IEC 61850 MMS, vendor REST | reported P/Q, ramp setpoint, trip thresholds |
| BESS controller | DNP3, Modbus | charge/discharge schedule, SOC reporting |
| RTU / IED | IEC 61850 GOOSE, DNP3 outstation | upstream telemetry aggregation, commands |
| DERMS / EMS | REST APIs, IEC 61850 client | dispatch commands across many DERs |
| Cloud aggregator | TLS APIs, OAuth tokens | multi-utility blast radius |
| Communication bus | network layer | replay, drop, or reorder messages |

## Attack-class → energy-impact pathway
| Attack class (used in code) | Primary STRIDE | Direct effect | Energy outcome |
|---|---|---|---|
| `fdi` | Tampering | DERMS sees inflated/deflated P → wrong dispatch | voltage deviation, ramp violations, possibly ENS |
| `replay` | Spoofing + Tampering | DERMS thinks system is in a past state → stale dispatch | mismatched P/Q vs. real load, voltage excursion |
| `command_spoof` | Spoofing | Inverter receives forged setpoint → executes harmful schedule | curtailment (FP) or over-injection / trip (FN) |
| `dos` | DoS | Telemetry/command path goes silent | DERMS open-loop → ramp + voltage drift |
| `firmware` | Tampering + EoP | Inverter logic altered | persistent off-spec behavior, hard to roll back |

## Detector-error cost model
For each scenario the run produces:
- `gt_attack(t)` ∈ {0,1} from `ground_truth_active_attacks` in `decisions.jsonl`
- `det_attack(t)` ∈ {0,1} from `detection.attack_class != "none"`
- a vector of energy-impact metrics (Step 2)

We define operational cost per run as
```
C_run = w_ENS · ENS + w_curt · curtailed + w_volt · voltage_dev + w_safety · I[max|Δf|>band]
```
where `w_*` are utility-supplied weights (paper reports two weight regimes: a
"reliability-leaning" set and a "cost-leaning" set). FP and FN curves are then
generated by sweeping the detector's confidence threshold and recomputing
`C_run` — see `code/evaluation/cost_curves.py`.
